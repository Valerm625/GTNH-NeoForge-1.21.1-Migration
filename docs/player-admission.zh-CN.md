# 世界启动与原生玩家加载接入

本阶段把世界绑定与加载来源凭据接入固定 NeoForge 21.1.262 的原生调用位置。已编译适配器、执行生产凭据/保存许可模型，并在客户端和独立服务端分别完成隔离 Sponge 变换。没有启动真实 Minecraft 世界，不能把“已注册”解释为原生生命周期或完整迁移已验证。

## 启动和关闭

`MinecraftServer.loadLevel` 首部调用 `LegacyQuestNativeLifecycle.beforeWorldLoad`。固定字节码确认独立服务端在 `initServer` 中先设置 PlayerList，再调用 loadLevel；集成服务端在构造时设置 PlayerList。入口先取得原生保存/生命周期范围，再检查世界绑定，元数据读取失败也不能进入无保护的清理保存。

没有迁移元数据的世界不创建账本，释放范围后继续原生流程。存在元数据时必须通过 `LegacyQuestWorldStore.open` 重开，且玩家列表为空。它先用[房主事务恢复器](owner-transaction-recovery.zh-CN.md)核对世界来源，并修复同一待决事务中已知旧/新状态的镜像与缓存；在普通离线决策前检查加载标签，决策后再次检查已解决的缓存与标记。期间原生保存和玩家生命周期调用受范围保护；实际游戏中的其他模组兼容性尚未验证。

成功后账本保持排他打开，供后续任务处理器通过 `LegacyQuestNativeLifecycle.world(server)` 使用。正常 `stopServer` 返回后关闭账本。初始化失败保留隔离状态；当前故障停止可能被保护拒绝，锁和隔离可能持续到进程退出，尚未实现完整安全故障关闭。不要用普通断线来绕过它。

历史目录仅用于解释既有账本。正式新提交仍需协调器核对当前可信定义和身份映射；此处没有自动导入旧包存档、自动创建定义目录或开启所有任务。

## 玩家入场

`PlayerList.placeNewPlayer` 调用自身 load 的位置现由适配器包裹，范围覆盖准备凭据、原生 load、加载事件和加载后的复核。它保留原来的分支：房主且世界 Player 标签非 null 时走世界缓存，其他情况走 UUID 文件，包括房主标签为 null 的分支。

凭据绑定同一世界账本 Head、玩家 UUID、当前线程和严格读取的文件快照：

- 普通玩家必须读取当前 `playerdata/<UUID>.dat`。原生压缩读取调用点获得这份已复核快照的副本，之后仍执行原生 DataFixer、Entity.load 和模组加载事件。
- 房主的加载标签必须与权威世界文件在 UUID、Inventory 和事务标记上一致；实际进入 Entity.load 的完整标签还必须与凭据捕获值一致。
- 首次登录只有在没有此玩家事务历史、当前文件和旧备份均不存在时成立。曾取消事务、因而标记为空的玩家仍属于有历史，不能因为当前文件丢失而被重建为空玩家。
- 原生主文件失败后的备份操作被单独保护，避免原生 catch 吞掉读取异常后复制损坏文件。首次登录的空备份路径保留，但需要再次确认两个文件都不存在。

`Entity.load` 首部对 ServerPlayer 检查玩家、来源凭据和一次性许可，其他实体保持原生行为。正常路径只允许同一玩家的 `PLAYER_LOAD → PLAYER_FILE_LOAD → PLAYER_NBT_LOAD`，或者房主的 `PLAYER_LOAD → PLAYER_NBT_LOAD`。回调中的重复加载、切换玩家或保存不能借用这个许可；即使违规异常被回调吞掉，范围仍保留失败状态。

加载结束后确认返回值仍是已允许加载的那个 NBT 对象，并从实际玩家 UUID 和 NeoForge 持久数据重新检查事务标记，避免加载事件把标记清除后仍放行。正常加载事件对玩家背包的合法变化不与旧库存强行比较；原生读取及 DataFixer的实际行为仍需要游戏测试。最终再次检查文件全文摘要、清单和账本 Head，成功后释放范围，再继续原生入场流程。

这不是任意模组的安全沙箱：反射、其他未审计载入入口、外部文件写入者和任意背包修改仍需要单独处理。绑定世界中直接调用 PlayerList.load 或 PlayerDataStorage.load 的其他模组需要适配到统一入口，不能因为原生调用位置通过隔离检查就声称全部模组兼容。

## 验证与尚未完成的路径

`test_legacy_quest_player_admission.py` 执行 **89 项断言**，另有 **4 个独立 JVM 中断后的恢复与加载凭据场景**。包括普通/房主成功路径、首次登录、房主 null 标签分支、待决事务、损坏文件、旧备份、丢失但有历史的玩家、来源变化、重复或跨线程使用、加载回调保存、返回值替换、事件后的实际玩家标记丢失及 UUID 变化。数据和实际玩家对象的端口仍为夹具，没有真实玩家存档。

原生 Mixin 检查现在覆盖客户端 **39 处注入/7 个目标**、独立服务端 **38 处注入/6 个目标**；同时检查变换后 DataFixer → 加载 → 事件的调用顺序。缺失保存目标、缺失加载目标和缺失注册三组负例会被检测。ASM 数据流与固定字节码检查不证明完整 NeoForge 转换链、JVM 类链接或实际游戏行为。

旧 v1 事务标记仍可读，但本入口要求持久升级完成后才能入场；[独立标记维护日志](player-marker-upgrade.zh-CN.md)已接到启动恢复及凭据创建之前，保留原始文件并在合成文件中验证持久升级。真实原生路径仍未运行。已知待决事务的镜像/缓存错位已有独立恢复协议；未知冲突、初始化中断、模式/房主变化、外部整体回滚以及故障关闭都仍有待修复路径。当前拒绝并保留数据是阶段性行为，不能永久保留这些缺口后宣称完整迁移。
