# 房主中断事务的镜像与缓存恢复

`LegacyOwnerTransactionRecovery` 在原生世界加载前处理待决 `WORLD_PLAYER` 事务。权威 `level.dat/Data/Player` 必须证明同一日志事务的旧状态或新状态；现存 UUID 镜像和已加载缓存也必须分别证明该事务的旧/新状态。以世界文件选择提交或取消，再让镜像和实际缓存一致，最后记录任务进度决策。

这是对已有持久事务协议的恢复，不是将任意背包差异解释为可退款或可重扣，也不是整个旧 GTNH 存档转换器。

## 原生入口和写入顺序

`LegacyQuestNativeLifecycle.beforeWorldLoad` 持有原生保存保护和世界账本句柄，要求服务器线程及空玩家列表。顺序是：恢复已有标记维护意图 → 恢复房主事务及辅助状态 → 检查待决世界缓存 → 普通离线事务恢复 → 检查已解决缓存 → 旧房主标记升级。新恢复器不会为普通 UUID 事务猜测世界来源。

恢复记录在 `<world>/gtnh-migration/owner-transaction-recovery/`：

1. 原始世界文件、原始 UUID 镜像与目标镜像的完整 gzip 字节进入不可变、按 SHA-256 寻址的 `blobs/`。
2. 追加式 `ledger/` 首帧绑定世界清单原件，准备记录绑定主账本确切版本/摘要和原事务准备摘要。
3. 再次检查所有来源、缓存及主账本后，强制写入同目录临时文件，再原子替换 UUID 镜像并严格读回。已经一致的镜像保持原压缩字节。
4. 实际加载缓存只更新 Inventory 和本项目两种标记位置，其余缓存特有字段保持。
5. 最终再次确认原世界全文摘要、目标镜像及缓存一致，才由原主日志以世界快照决定提交或取消；随后追加辅助恢复完成记录。

世界文件与 `.dat_old`/`level.dat_old` 始终不改写。镜像中的其他模组数据来自当前镜像，不从世界快照整体覆盖。镜像缺失、损坏、UUID不符或库存/标记不构成日志已知状态时保留现状并拒绝；缺失镜像与其他未知冲突的完整修复仍待实现。

## 中断与历史核验

进程可在原件归档后、意图发布后、镜像发布后、缓存更新后、主日志决策后及辅助完成后退出。重开时仅接受当前镜像的完整摘要等于归档原版或目标版；世界全文必须保持原样。缓存可以是同一事务的已知旧/新状态，最终必须与世界选择一致。

特别处理“主日志已决策、辅助恢复尚未完成”的间隙：验证主账本紧接准备帧的决策、事务UUID、准备摘要和来源记录，再完成辅助记录，不重复写入任务决策。主账本已经前进到其他事务时不会用旧恢复意图覆盖文件。历史辅助记录继续核对相应主决策，之后发生的新事务不强迫当前玩家回到旧标记。

文件账本新增按历史版本读取的包内接口；返回任意历史帧前仍验证整条链，不以单个旧文件代替当前完整历史。主日志提供经验证的历史准备/决策读取，恢复记录不能引用其他事务或任意历史版本。

旧标记维护与房主恢复互斥。即使主日志已经完成、房主辅助记录尚待完成，也不能插入标记升级去改变权威世界文件；相反，仍有标记维护意图时也不能开始房主库存恢复。两个协议的异常状态都保留原件和意图，不删除目录来解除拒绝。

## 二进制与缓存保真

共享的包内 `LegacyPlayerNbtPatch` 沿原始命名字段范围编辑，只替换镜像 Inventory 及本项目事务标记，其他 NBT 字节和根名称保留。事务标记升级复用同一解析器，原来的黄金文件与拒绝案例继续验证。

恢复测试用独立编写、固定字段顺序的世界/镜像黄金文件，包含所有 NBT 类型、负零、NaN载荷、不同根名称及不同的世界/镜像私有字段，逐字节验证结果。恢复原事务的 v1 标记与本轮升级 v2 是两个独立步骤；移动/新增本项目字段时按编辑规则追加，不重排其他字段。

对象比较和来源日志保留对象中仍存在的 NaN 位模式；Minecraft 原生读取器可能已经规范化负零。此处证明定点二进制编辑保留不修改的字段，不代表真实 Player 全加载/保存流程或所有模组组件已经保真。
