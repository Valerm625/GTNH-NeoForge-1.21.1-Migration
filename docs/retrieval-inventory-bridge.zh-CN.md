# 真实 Minecraft 库存快照与计数应用

Phase 5 的 `LegacyRetrievalInventoryBridge` 将现有顺序规划器连接到实际 1.21.1 `Inventory` 和 `ItemStack` 对象。它已经执行真实对象的计数修改、完整槽位复核、异常回滚和重入隔离，但**没有注册游戏提交入口，没有保存玩家档案，也没有将进度与库存组成持久化事务**。任务导出和物品身份映射数量均不增加。

## 快照与匹配身份

`prepare` 接收已验证的 quest 声明、之前任务状态、actor、原参与者顺序、在线成员库存和 `HolderLookup.Provider`。它保留调用者给出的在线扫描顺序，不对 Set 的枚举结果作源顺序假设。Context 继续校验 actor 必须在线，在线 UUID 属于全体成员；同一个 Inventory 对象不能同时归给两个 UUID。实际非空 Player 的 UUID 也必须与该库存键一致。

读取范围严格为 `items[0..35]` 和 `armor[0..3]`，映射旧槽位 0..39。副手不计入检测、不扣除，也不因副手变化使本次旧式检测失效。另外检查对象引用别名：多个观察槽位共享同一个非空可变栈、或观察槽位与副手共享同一个栈时拒绝，防止仅改actor count却连带改变其他槽位。此检查不把副手内容计入旧任务。未知主背包/盔甲布局和负数计数拒绝，不截取或猜测布局。

`FrozenStack` 使用真实 ItemStack NBT 编解码保存 count=1 的身份，并比较往返前后的完整 item/components 与 NBT 编码。内部只留 NBT 深副本及注册表 provider，每次 `stack()` 都从副本重新解码，不向匹配谓词泄露共享 ItemStack。调用者不得把“可以无损保存”当成“符合旧任务匹配”：旧 meta、耐久/NBT 和 ore 集合仍需独立匹配器。只可网络同步、不能持久化或不能稳定往返的组件明确拒绝，原库存保持原样；这些类型的完整支持仍是缺口。

快照以 count 和完整编码核对真实槽位，因此即使任务匹配规则忽略耐久，提交时也能发现耐久变化。对非消耗物品、空槽以及其他在线参与者的旧40槽同样复核。现代注册表和定义/映射 revision 的稳定性仍由运行时协调器核对，不能跨世界或跨配置复用一个 Prepared。

## 应用顺序与边界

`Prepared.plan()` 是不可变计算结果。应用入口明确命名为 `applyCountsWithoutPublishing`：

1. 要求使用创建 Prepared 的同一线程、每个 Prepared 最多尝试一次、源 gate 已允许检测。创建线程不一定是服务器线程；未来游戏入口仍须显式核验服务端主线程和认证连接。
2. 为所有观察库存取得身份级别的应用保护，拒绝重叠或嵌套应用。前次回滚不确定的库存对象继续被拒绝。
3. 调用 precondition 复核定义、账本 revision、参与者和权限，并在其后重新核对全部观察槽位。precondition 是调用方合约，不是此类自动完成了服务器权限或队伍验证。
4. 核对计划只有 actor 计数减少，并与全部 Consumption 的槽位、身份和总量一致；不允许改变参与者库存、添加物品或扣除其他成员。
5. 在完整复核通过后应用整个 quest 的最终计数。未清空的槽保留原 ItemStack 实例，仅改 count，保留 popTime 等附属运行状态；清空的槽设为 EMPTY。不会逐任务发送 FTB 回调、事件、奖励或广播。
6. 再次复核最终槽位和前置条件。正常返回后仍不 markDirty、不改变 Inventory 的 timesChanged、不广播菜单、不写文件。后续必须由真实持久化协调器完成库存/进度协议，再发布变更。

RuntimeException 或 Error 触发反向计数回滚，恢复原对象及计数。若槽位已被另一个操作替换，拒绝用旧栈覆盖新栈；回滚后也重新检查全部观察槽位。任何未恢复状态使涉及的库存对象进入 `recoveryRequired`，无清除快捷接口。该标记只存在于当前进程的库存对象上，不能跨重启保证恢复；持久化的未决事务日志与玩家水位仍未实现。

这不是对任意模组回调副作用的完全回滚保证。当前独立测试使用基础 Minecraft 类，没有 NeoForge 转换链、第三方 Inventory/ItemStack Mixin 或世界事件。未验证的副作用不能以通过纯模型或当前真实对象测试代替。检测成功也不会自动把任务状态写入 UUID 账本；若先扣物后单独保存账本，崩溃仍可能丢物或重复扣物，正式提交入口在恢复协议完成前不得这样连接。

## 证据与仍缺部分

`test_legacy_retrieval_inventory_bridge.py` 使用固定 Minecraft JAR、真实 `Inventory(null)` 和真实物品栈，已通过 **1,465 项断言**：

- **1,332 个非空原版默认物品栈**均能保存和还原身份；包含嵌套 custom data、命名与耐久变化、返回值隔离及不持久化组件的拒绝案例。
- 全部40槽逐槽改变均使旧计划失效，包括未扣槽和其他参与者；副手排除、盔甲39号槽完整消费、非首位 actor、离线 UUID 与参与者扫描顺序得到检查。
- 9 gravel + 5 oak logs 的示例先检测再扣2，实际 Inventory 剩3；交换源任务 index 后检测结果随之改变。重复 Prepared 拒绝，使用保留 latch 的新计划不再次扣物。
- 跨槽应用中途异常、发布前置变化、嵌套提交、异线程调用、Error 回滚、外部替换不覆盖及不确定库存拒绝再次应用均覆盖。

该示例使用明确的原版 OAK_LOG 谓词，不是旧 `logWood` 成员映射。世界、Player 实例、认证/队伍、配方/科技门槛、同步、完成/奖励和玩家存档均未测试。1,332项物品栈往返不能计作1,332项旧物品迁移。真实源差分仍由已有 engine/planner 检查提供；本检查没有新宣称运行原1.7.10游戏。

报告为 `evidence/quests/LegacyRetrievalInventoryBridgeCheck.json`。完整重建验证本检查使用的桥接生产类与兼容 JAR 对应类逐字节一致。下一步需要实际世界生命周期、准确物品/ore 匹配、玩家持久化水位与账本恢复协议，然后连接手动请求、队伍/完成/奖励和 UI；完整目标不变。
