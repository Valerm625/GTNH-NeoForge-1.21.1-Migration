# 检索提交协调器与原生保存适配

`LegacyRetrievalCommitCoordinator` 把已有独立账本、库存桥接、标记和玩家文件读回串成一条提交流程。公开入口接受真实ServerPlayer及PlayerDataStorage，并调用原生saveWithoutId、getPersistentData和save；代码已针对锁定NeoForge server编译。测试通过包内保存接口注入故障，未实际运行ServerPlayer或原生保存方法。当前没有注册游戏事件或提交消息入口。

## 提交顺序

1. 校验库存对象属于actor、计划仍可使用、线程与所有参与者槽位未变、账本完整Head等于规划时快照，以及外层授权条件。不能只拿相同摘要包装不同的状态，也不能复用已经尝试过的计划。
2. 按已解决日志核对玩家标记，必要时将旧v1升级到PlayerPersisted中的v2。调用保存后读取当前UUID.dat，确认库存和标记与内存一致，再允许准备事务。其他模组的持久数据保持原样。
3. 用已确认的磁盘基线生成候选，追加准备记录。账本暂不提交新进度。
4. 重新检查基线文件及条件，应用实际库存计数，再只更改本项目的标记字段。调用原生保存接口；返回成功与否都不能替代读回。
5. 当前UUID.dat中标记和库存都与新候选一致，且内存也一致时，才提交账本进度。保存器在发布文件后抛异常，仍以文件证据判断；诊断保留在Outcome中。
6. 当前文件证明仍是旧状态时，先恢复本次扣减的原物品对象和数量，再恢复旧标记。全部内存与磁盘复核通过后才发布取消记录；不会为了取消而再次保存玩家文件。

恢复已完成计数应用时，先检查所有参与者的40槽后状态，并预查每个原始物品对象。整栈移除后仍保存原对象引用；它在脱离库存期间被改动，也会阻止恢复。其他代码替换了槽位对象时，即使替代物看起来相同，也不覆盖它。没有全玩家NBT加载，没有按旧快照重写其他模组数据，没有发放奖励或广播UI。

## 不确定结果

无法读取当前文件、标记与库存不构成合法前/后状态、外部改动物品、账本写入结果不确定，都会保留现有文件及待决记录（若准备已发布），并让本次账本对象及参与库存进入拒绝再次提交的状态。正常保存方法吞掉异常但磁盘仍是旧状态时，可以按上述取消路径恢复；不可判断时不能猜测退款或继续扣减。

`RecoveryRequiredException` 要求调用层继续隔离玩家和写入。这里的内存标记只约束本桥接/协调器，不会停止普通游戏tick、原生保存、断线或登录。不能把普通断线当作隔离操作，因为退出流程可能保存不确定的库存。原生生命周期隔离尚未实现，因此该类不能单独激活为联网提交入口。

持有账本监视器和协调器重入保护不等于锁住所有玩家文件。调用者必须持续排除其他保存、库存变更、死亡/克隆/退出、参与者变化及直接账本写入；传入的assertExclusive只检查外层隔离状态，不创建隔离。外部文件写入者也不受它控制。当前只检查服务器线程与Player未removed；认证、原BQ入口条件、队伍和世界存储归属仍由可信调用层负责。
